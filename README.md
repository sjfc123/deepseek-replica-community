# DeepSeek Replica · 社区二创版

> 一个 Android 上的本地优先 AI 聊天客户端。日常聊天能用，角色卡、世界书、场景、长期记忆和语音通话也能跑。  
> 这里只放源码，不发布 APK。

这个仓库不是从零写出来的。它的底子是 [LiJiaHua1024/deepseek-app-replica](https://github.com/LiJiaHua1024/deepseek-app-replica)，一个尽量复刻 DeepSeek 手机端交互的 Android 客户端；后来又从赤石科技的 [YanJiuWeiYuanHui/DeepChat](https://github.com/YanJiuWeiYuanHui/DeepChat) 移植了一部分对角色扮演真正有用的能力，再加上这段时间的改动，慢慢长成了现在这个样子。

最早要解决的其实只有一个问题：自定义接口一填，`system` 被整个置空，角色立刻开始出戏、复读、答非所问。修完这个 bug 之后，才发现后面还有一串问题：长对话被摘要改写成“关于角色的元叙述”、角色卡和手写提示词互相覆盖、世界书没有命中逻辑、记忆跨分支串线、语音通话被 WebView 掐断、升级后白屏、页面能滚动但整页点不动。很多功能不是提前规划出来的，是被这些具体故障一步步逼出来的。

## 现在能做什么

**日常聊天**

Markdown、表格、代码块、KaTeX 公式、Mermaid 图表都能渲染；支持图片与文件、联网搜索、回复朗读、分支与重新生成、会话分组、归档、批量操作、主题和气泡样式、自动备份、历史导入导出。它首先是一个能日常使用的聊天客户端，不是只能拿来跑角色的演示壳。

**角色扮演**

角色卡最多 50 张，支持自定义头像、标签筛选、开场白、内置的大肥鱼 / 鲸鱼娘 / 猫娘三张卡，也能导入 Character Card V2/V3、TavernAI 和 PNG chara。世界书最多 100 条，支持关键词或正则命中、常驻条目、按角色绑定和单轮预算；场景可以手填，也可以按轮自动提取。

角色侧还有内心独白、动作样式、`{{user}}` / `{{char}}` 占位符、玩家括号独白、称呼约定和长消息折叠。最终 system 的组装顺序是：记忆 → 场景 → 世界书 → 角色卡 → 手写提示词。

关闭角色扮演时，当前角色卡的人设可以保留，世界书、场景和演出规则暂停；重新打开就恢复完整扮演。这样不会因为临时关掉扮演，把已经调好的角色和旧对话一起清空。

**记忆、通话和成本**

长期记忆按会话分支隔离，支持关闭、整轮记录、自动提炼三种模式，卡片可编辑、删除、手动补充，上限最高 9999 张，字符预算默认 1M。记忆可以单独导出导入，角色卡、头像、世界书、场景可以打成设定存档，整个会话也能单独导出。

语音通话是连续的：VAD 断句、ASR 转写、流式回复分句 TTS、播放中插话打断。没有活动会话也能直接开麦，首条转写会新建会话并生成标题。网页采集被系统拦下时，会尝试切到原生 `AudioRecord`；读取中断会自动重建，最多两次。

另外还有 Token 实际用量、会话统计、九个真实耗 Token 开关的集中说明、峰谷时段提示、诊断日志和启动公告。它们不直接让角色变得更好，但能让你知道钱花在哪、问题出在哪、下次升级会不会把数据弄丢。

## 二创具体改了什么

不是简单换皮。主要动了四块：

1. **请求层**：修掉自定义接口下 `system` 为空的问题；把角色卡、世界书、场景、记忆、手写提示词按固定顺序拼进 system；补齐 Chat / Responses / Anthropic / 自定义网关的请求差异、采样参数、拒答处理和标题策略。
2. **角色层**：重做角色卡、世界书、场景、标签、开场白、头像、内置卡、导入格式和角色表达样式。原来的“提示词输入框”变成了一套可切换、可保存、可导出的角色配置。
3. **记忆与数据层**：长期记忆从单轮文本变成按分支隔离的卡片系统；补上记忆归档、会话包、设定存档、自动备份和 Token 账本。
4. **稳定性与产品化**：处理白屏、闪退、TDZ、`inert` 卡死、低端 GPU 黑帧、长会话动画泄漏、诊断日志误报，以及设置搜索、主题、峰谷提示、成本页这些长期使用才会需要的东西。

## 只开源，不发 APK：具体原因

这句话不是免责声明里的摆设，也不是“留一手”。开源代码和分发安装包是两件不同的事：前者交出的是可检查的实现，后者交出的是“我替你签过名、我保证它能装、出了问题找我”的信任。后者我现在给不了，原因至少有以下几条。

### 1. 签名和更新链没法一起交出去

二创用的是个人调试签名，不是可以长期持有的发布证书。继续发 APK，就等于让所有人信任一把在我手里的钥匙；以后不维护了，这把钥匙也不该继续代表这个软件。更麻烦的是更新链：没有稳定的发布仓库、签名校验和回滚方案，所谓“最新版”只是一个随时可能失效的下载链接。

### 2. 二进制不能自证

源码能看、能 diff、能自己编译，APK 不能。一个被重新签过名的包，图标、版本号、关于页都可以做得一模一样，里面多了一个权限、一个上报地址，普通用户看不出来。仓库如果只发源码，至少每个人都能从同一份代码开始验证；发一个成品包，反而把“信我”变成了安装前提。

### 3. API Key 和聊天记录不是演示数据

这个应用要填自己的 API Key，会话、角色卡、记忆和附件都落在本机。一个来路不明的改包，最坏的情况不是闪退，是密钥和聊天内容被带走。源码公开、用户自己构建，至少能把“谁编的、从哪来的”查清楚；直接分发 APK，我没法替一个无法验证的包承担这种信任。

### 4. 上游代码和素材的授权边界

基础工程是 GPL-3.0，DeepChat 和 chat-demo 是 MIT，内置角色卡、头像和部分社区设定又牵涉角色形象与二创素材。源码仓库可以保留 LICENSE、NOTICE、MIT 全文和逐项署名；做成 APK 往外发，就会把代码许可、角色素材、商标和平台规则混成一笔账。这个边界不该由一句“仅供参考”糊过去。

### 5. 平台规则和分发责任

应用商店、企业分发、侧载渠道各有自己的审核、隐私披露、年龄分级和合规要求。这个仓库没有开发者账号，也没有为上架做过合规审查。把 APK 挂出去，等于默认替它承担这些责任；我没这个能力，也不想用“开源”两个字把责任转给下一个人。

### 6. 没有长期维护能力

二次开源之后，不负责往后的更新，也不分发 APK。软件还在观察期，系统版本、WebView、麦克风权限、厂商 ROM 都会变。继续挂安装包，只会制造“有人在持续维护”的错觉；用户装上一个不再更新的包，出了问题连该找谁都不知道。

### 7. 防止被拿去冒充

仓库不提供“官方包”，别人拿一个 APK 来冒充这个项目时，至少还能要求他给出提交记录和构建方式。一旦有了官方下载链接，伪造包就有了天然的话术：“这就是那个项目的安装包，只是我重新签了一下。”

### 所以，实际怎么用

- **想自己用**：按上面的构建步骤编译，自己生成签名，自己承担系统兼容、API 费用和数据备份。源码许可证允许你自己构建和使用。
- **拿到别人转发的 APK**：先问清楚对应的提交、构建命令和签名来源。答不上来就不要装，更不要在里面填 API Key。它不是这个仓库发布的，我无法保证它没有被改过，也无法替它背书。
- **想再分发**：GPL-3.0 允许符合许可证的再分发，但那是“你编译的版本”，不是这个仓库的官方包。请保留 LICENSE、NOTICE、上游署名，自己处理角色素材、商标和平台合规。不要把“二次开源”理解成“谁都可以拿这个名字发一个包”。

这个仓库的交付物只有源码。你可以自己编译、自己签名、自己装；编译出来给谁、怎么用、出了问题怎么办，都由你自己承担。我不反对个人自用或小范围测试，反对的是把没有来源的成品当成这个项目的官方版本流通。

## 构建

前端：

```bash
pnpm install
pnpm type
pnpm build
```

构建产物在 `dist/`。

Android 工程保留在 `android/`，当前配置使用 Gradle 9.7.1、AGP 9.4.0、compileSdk 37、minSdk 29。环境版本对不上时，按自己的 SDK 调整 `android/app/build.gradle`：

```bash
cd android
./gradlew assembleDebug
```

仓库不附带 `release.jks`、`debug.keystore` 或任何签名文件。需要发布包时，自己生成并保管签名；不要把密钥提交进来。

应用内的更新检查入口保留为空仓库地址，默认不会去 GitHub 拉 APK。想接自己的发布源，再填 `UpdateRelease.java` 里的 `REPOSITORY`；本仓库不提供可下载的成品。

## 数据与隐私

- 没有账号体系，也没有中转服务器。API Key 由你自己填，Android 侧走 Keystore 加密存储。
- 会话、角色卡、世界书、场景、记忆和附件都保存在设备本地。卸载应用会清掉本地数据，重要内容先导出。
- 请求只会发往你配置的接口地址。你用了哪个网关、那个网关怎么记录请求，不在这个仓库的控制范围内。
- 导出的备份不包含 API Key；角色卡和设定存档是否含图片，以导出时的提示为准。

## 使用边界

这个项目是工具，不是官方客户端，也不是内容平台。不要拿它做违法、侵权、骚扰、冒充官方或绕过平台规则的事。AI 生成的内容、API 费用、账号状态和对话后果，都由使用者自己承担。

这不是一个有 SLA 的商业项目。Issue 可能回，也可能不回；兼容性问题、系统差异、厂商 ROM 的限制，需要自己排查。仓库里能做的，是把代码和边界写清楚，不能替每个人保证“在你这台机器上一定没问题”。
